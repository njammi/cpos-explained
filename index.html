A governance system for AI-assisted work

CPOS — the Claude Project Operating System

One standard, many projects. CPOS is how a single person keeps a growing pile of AI-assisted projects honest, current, and easy to pick back up — without re-explaining the same context to the AI every session, and without one project's fix quietly failing to reach its siblings.

The problem it solves

Running one AI-assisted project is easy. You talk to the AI, it remembers what you told it earlier in the conversation, and when the conversation ends, you remember the rest yourself.

The trouble starts around the third or fourth project. Each one has its own conventions, its own half-finished decisions, its own idea of what "done" looks like. A useful pattern discovered in one project never makes it to the others, because nothing carries it across. Documentation quietly goes stale in the projects you're not currently looking at. Six months later, nobody — human or AI — can say with confidence what state any given project is actually in.

CPOS treats that as a governance problem, not a documentation problem. It separates two roles that are easy to blur together:

The standard

One canonical definition of how a project should be structured, documented, and scored. Lives in one place. Projects reference it — they never copy it.

The projects

Each one owns its own content, decisions, and voice. The standard governs their shape, never their substance.

A dedicated "Architect" repo holds the standard and audits every project against it. It owns no project's content — only the rules every project is measured by, and the standard itself is versioned, so it can improve without silently rewriting history.

The file model

Every governed project carries the same small set of files. Nothing exotic — just enough structure that a new session (human or AI) can get oriented in under a minute, without reading the whole repository.

CLAUDE.md

Operating instructions

Deliberately thin. States the mission in a sentence or two, points to the standard for behavior, and lists only what's project-specific: startup files to read, hard rules, things never to do without approval.

PERSONA.md

Who's advising

The expertise, voice, and judgment the AI should bring to this project — a growth strategist for a Shopify brand reads nothing like a curriculum designer for a coding course, even though both follow the same standard.

WORKSPACE.md

Current state

What's done, what's in flight, what's blocked, and the next concrete step. Read first every session; updated at the end of any session that made real progress.

DECISIONS.md

Settled calls

Long-term decisions, recorded once. Future sessions respect them automatically instead of re-litigating the same trade-off every few weeks.

Other files — TODO.md, ROADMAP.md, a memory log — get added only once a project's real work earns them. Nothing is scaffolded on the chance it might be useful someday.

Two ways of measuring health

CPOS scores two different things, and it's worth keeping them apart. Compliance asks whether a project follows the standard's structure. Health asks whether the project is actually in good shape. A project can be perfectly compliant and still be stalled, undocumented in spirit, or drifting — compliance is necessary, not sufficient.

Compliance — 10 checks, 10% each

  • CLAUDE.md exists and stays thin
  • No embedded copy of the standard itself
  • PERSONA.md defines a role that fits the project
  • WORKSPACE.md reflects current state (or genuinely has none yet)
  • DECISIONS.md exists once real decisions have been made
  • Clear next actions exist somewhere
  • The repository root is clean
  • Documentation matches reality on a spot check
  • No duplicated documentation
  • The project is registered and current in the index

Health — 6 dimensions, scored 0–10

  • Documentation — coverage, accuracy, freshness
  • Repository organization — structure and root hygiene
  • Outstanding tasks — are next steps captured and current
  • Decision tracking — are decisions recorded and respected
  • Technical debt — inverse of accumulated shortcuts and drift
  • Compliance — the 10-check score above, folded in as one dimension

A project can score 100% compliant with a completely empty repository — a scaffold with nothing in it yet passes every structural check. That's why sandbox and archived projects are registered but explicitly exempted from scoring, rather than given a number that would only measure emptiness.

Governance has a rhythm, not just a rulebook

A standard nobody revisits calcifies. CPOS runs a recurring cycle so drift gets caught on a schedule, not by accident:

  1. Discovery sweep — list the top-level folders that could contain a project, and flag anything real that isn't registered yet.
  2. Audit — score every registered project against the standard.
  3. Refresh health scores — update the six-dimension view for each project.
  4. Harvest lessons — review what's been learned since the last cycle, and decide what's proven enough to promote into the standard itself.
  5. Write the report — one document, dated, that a future session (or a future person) can read to understand what changed and why.
  6. Recommend what to invest in next, ranked by impact — not a list of everything that could be improved.

One more rule matters as much as the cycle itself: the governance layer never writes into a project while someone might be actively working in it. Before touching a project's files, it checks for recent activity — modified files, uncommitted changes it didn't make, a running process — and defers if anything looks live. Reads are always safe; writes wait for a quiet moment. Audits, in particular, are read-only by design — findings get written to the governance layer's own reports, never into the project being audited.
